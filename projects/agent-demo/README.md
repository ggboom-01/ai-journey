# agent-demo · 我的第一个 Agent

> 一个不到 250 行、零依赖的最小 Agent 实现。
> 不用 Colab、不用 API Key、不联网 —— 全程跑在本机的 Ollama 上。

## 这是什么

大部分人说的"我用 AI 做了个东西"，其实是"套壳聊天机器人"：把问题转发给模型，把回答显示出来。

**Agent 不一样。它多了一个东西：模型可以自己决定去调用工具。**

```
聊天机器人：  你问 → 模型答（全靠它脑子里记的东西，算错了也照样自信）
Agent：      你问 → 模型说"我需要查时间" → 真的去查 → 拿到 2026-09-24 00:14
                   → 模型说"我还需要算这个" → 真的去算 → 拿到 69893
                   → 模型结合真实结果作答
```

差别在哪？**模型碰到了真实世界。** 它不再靠猜，而是拿到了真实数据。

## 快速开始

前提：[Ollama](https://ollama.com) 已安装，并且拉过一个模型：

```powershell
ollama pull qwen3:4b
```

然后：

```powershell
cd D:\ai-journey\projects\agent-demo
python agent.py "现在几点了？顺便算一下 (1234*56)+789 等于多少"
```

或者直接双击 `run.bat`（不带参数会跑上面这个默认问题）。

**实测输出**（本机 RTX 环境，qwen3:4b，约 13 秒）：

```
[你问] 现在几点了？顺便算一下 (1234*56)+789 等于多少
[模型] qwen3:4b

--- 第 1 步 ---
[模型决定] 调用 get_time({})
[工具返回] 2026-09-24 00:14:57
[模型决定] 调用 calculator({"expression": "(1234*56)+789"})
[工具返回] 69893

[最终回答] 现在是2026年9月24日 00:14:57，(1234×56)+789 等于 69893。
```

注意看：**模型一次要了两个工具**，然后才作答。这就是 Agent 和聊天的分水岭。

再试一个需要多步的：

```powershell
python agent.py "sandbox 目录里有哪些文件？然后读一下 notes.txt，用一句话告诉我它讲了什么"
```

输出会先 `list_files` → 看到 `notes.txt` → 再 `read_file` → 才回答。**第 2 步的参数是它根据第 1 步的结果决定的**，这就是"链式调用"。

## 它是怎么工作的

整个 Agent 的核心就是 `run_agent()` 里那个 while 循环，只有 4 个动作：

| 步骤 | 代码里对应 | 发生了什么 |
|---|---|---|
| ① 提问 | `chat(messages)` | 把 **用户问题 + 工具说明书** 一起发给模型 |
| ② 思考 | `msg.get("tool_calls")` | 模型返回它想调用的工具和参数（也可能直接回答，那就结束） |
| ③ 行动 | `TOOLS[name][0](**args)` | **我们**真正执行这个 Python 函数，拿到结果 |
| ④ 观察 | `messages.append({"role": "tool", ...})` | 把结果塞回对话历史，回到 ① |

关键认知：**执行工具的是你的代码，不是模型。** 模型只会输出一段"我想调用 calculator，参数是 (1234*56)+789"的 JSON，真正的计算是你的 Python 函数做的。

所以 Agent 的能力上限 = 你给它写的工具的上限。工具写得好不好（尤其是 `description` 那段给模型看的说明书），直接决定它用得对不对。

## 当前工具箱

| 工具 | 作用 | 说明 |
|---|---|---|
| `get_time` | 获取当前时间 | 演示"模型不知道此刻是几点，必须问工具" |
| `calculator` | 数学计算 | 演示"别信模型心算"——大数乘法它经常算错 |
| `list_files` | 列出 sandbox 下文件 | 演示读取真实环境 |
| `read_file` | 读 sandbox 下文件内容 | 演示"参数由上一步结果决定"的链式调用 |

### 怎么加一个新工具

改两个地方就行。比如加一个"数一段文字有多少字符"：

```python
# 第一步：写函数
def tool_count_chars(text: str) -> str:
    return f"共 {len(text)} 个字符"

# 第二步：注册（带说明书）
TOOLS["count_chars"] = (
    tool_count_chars,
    {
        "type": "function",
        "function": {
            "name": "count_chars",
            "description": "数一段文字里有多少个字符。用户问'多少个字'时用它，不要自己数。",
            "parameters": {
                "type": "object",
                "properties": {"text": {"type": "string", "description": "要数的文字"}},
                "required": ["text"],
            },
        },
    },
)
```

然后问它："读一下 notes.txt，告诉我里面有多少个字符" —— 看它会不会自己串起 `read_file` → `count_chars`。

## 三个防止它"转圈圈"的设计

Agent 最容易出的问题是**死循环**：模型反复调用同一个工具，或者一直不给出结论。文件里有三道闸：

1. **最大步数** `MAX_STEPS = 8` —— 走不完就强制停
2. **总耗时上限** `MAX_SECONDS = 180` —— 卡住就强制停
3. **重复检测** `seen` 集合 —— 完全相同的工具调用出现第二次，直接拦截，并告诉模型"你已经做过了，请换方法或直接回答"

这三条是我在路线图里提过的"防死循环三板斧"，现在你能看到它们的真实代码长什么样。生产环境里这三条是**必配项**，面试也一定会问。

## 安全设计（也是面试考点）

- **不用 `eval`。** `calculator` 用 `ast` 解析表达式树，只允许加减乘除和括号。直接 `eval` 等于把整台电脑交给模型。
- **目录锁死。** `_safe_path()` 保证 `read_file` 只能读 `sandbox/` 里的东西，模型传 `../../密钥.txt` 会被拒绝。
- **不给危险能力。** 这个 demo 里没有"执行 shell 命令"这类工具。真要在生产里做，必须加人工确认。

## 练习（由易到难）

1. **换模型**：把 `MODEL` 改成 `qwen3:8b` 或别的，看响应质量和速度怎么变。
2. **加个工具**：按上面 `count_chars` 的例子加进去，跑通链式调用。
3. **制造一次死循环**：故意把 `MAX_STEPS` 改成 20，然后把 `calculator` 的工具说明删掉（让模型不知道该用哪个工具），观察它怎么卡住、三道闸怎么起作用。
4. **改成流式输出**：`payload` 里把 `"stream": False` 改成 `True`，处理逐块返回的 JSON 行——这是生产环境的标配。
5. **加记忆**：现在每次运行都是全新的。试试把对话历史存到 `history.json`，下次启动时读回来。

## 常见问题

**`ConnectionRefusedError` / `urlopen error`**
Ollama 服务没在跑。打开 Ollama 应用，或者命令行执行 `ollama serve`。

**`model "qwen3:4b" not found`**
模型名写错了或没拉下来。命令行执行 `ollama list` 看已有哪些模型，`ollama pull qwen3:4b` 拉取。

**模型不调用工具，直接瞎编答案**
小参数模型（4B）的工具调用能力有限。可以把 system 提示里的要求写得更强硬，或者换 `qwen3:8b` 以上的模型。

**终端里中文是乱码**
用 `run.bat` 启动（它会把控制台切成 UTF-8）。代码里也做了编码自适应。
